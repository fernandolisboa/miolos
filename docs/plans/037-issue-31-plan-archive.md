| `/arquivo/<YYYY-MM-DD>` | `app/arquivo/[data]/page.tsx` | a day: the games that date actually holds, one link each, plus a link up to its month |
| `/arquivo/<YYYY-MM-DD>/binairo` | `app/arquivo/[data]/binairo/page.tsx` | the playable archived Binairo |
| `/arquivo/<YYYY-MM-DD>/sudoku` | `app/arquivo/[data]/sudoku/page.tsx` | " |
| `/arquivo/<YYYY-MM-DD>/nonogram` | `app/arquivo/[data]/nonogram/page.tsx` | " |
| `/arquivo/<YYYY-MM-DD>/termo` | `app/arquivo/[data]/termo/page.tsx` | " |

**Date before game, and the game segment literal.** Date-first is the shape a human reads and the shape a month page's rows group under; it also keeps the four play routes as four *separate build outputs*, which is what stops Termo's ~36 KB validation dictionary from riding onto the archived Sudoku (D18's whole budget argument depends on it). ADR-0046 D1 is the precedent, stated in its own words: *"Literal, not dynamic: typed routes stay literal types, and the route boundary is what carries ADR-0011's per-game code-splitting. No `/modo-livre/termo` segment exists; the 404 is by absence."* Here the 404 is by absence for any fifth game, exactly the same way.

**Why not `/arquivo/<jogo>/<data>`:** it makes the game the collection and the date the leaf, which inverts what the archive *is* (a calendar of days, not four per-game histories), forces the index and month pages to fan out four times, and gives #34 a per-game share URL whose sibling days are unreachable by walking the path.

**Why a literal `mes` segment rather than a second dynamic level:** Next resolves a static segment ahead of a dynamic sibling, so `app/arquivo/mes/[mes]` and `app/arquivo/[data]/…` coexist without ambiguity. `/arquivo/mes` with nothing after it matches `[data]` with `data = "mes"`, which `calendarDateString` rejects → 404. Two dynamic segment *names* at the same position (`[mes]` and `[data]`) is a Next build error; this is the shape that avoids it without inventing a query parameter.

### D1a — `/arquivo/<hoje>/<jogo>` and `/arquivo/<hoje>` RESOLVE: a 307 to the daily route, not a 404 (Q1, revised)

**Decision:** when the requested date equals the DB clock's São Paulo today, the archive play route answers `redirect(routes[game])` and the day page answers `redirect(routes.home)`. Every *other* date is either archived (renders) or not published (404s, in SQL, inside the wall — `archivedWallPredicate` carries `date < SP-today`).

**Which clock decides, and the order the two reads run in (N2's fix — revision 2 specified a clock `apps/web` cannot read).** `todaySaoPaulo` is exported only on `@miolos/db/publishing`, which `eslint.config.mjs:85-94` bans in `apps/web`; the root barrel does not carry it. Revision 2's text therefore named a value the page could not obtain. The alternative in the repo — `todaySaoPauloDate(new Date())` (`apps/web/src/i18n/sao-paulo-day.ts:38`) — is a **second** clock: the web server's, on a different machine from Postgres. Its own TSDoc demands that any new caller clear the bar in writing, and this one cannot, because the skew is not theoretical: `archivedWallPredicate` decides "past" from the DB clock while the page would decide "today" from the web server's, so in the rollover window where they disagree `/arquivo/<D>/<jogo>` neither redirects (web says not-today) nor renders (SQL says not-past) — **a 404 on a URL the sitemap advertises**.

So **the DB clock is the only clock**, read through one new walled function (D4):

```ts
/** past | today | future, by the DB clock's São Paulo day. One statement,
 *  one clock, no table read. */
export async function archiveDateClass(db: Db, date: string): Promise<"past" | "today" | "future">;
```

**And the order is load-bearing.** Every archive page reads its content **first** and classifies only when the content read comes back empty:

1. `getArchivedDaily` / `listArchivedDays({from: d, to: d})` → **non-empty ⇒ render**. The archived path costs exactly one round trip and never consults the classifier at all; a row in hand *is* the proof that the date is past, so no comparison can contradict it.
2. Empty ⇒ `archiveDateClass(db, d)`. `"today"` ⇒ `redirect`. `"future"` or `"past"` ⇒ `notFound()`.

**The midnight straddle, specified rather than left implicit.** Two sequential statements can straddle the rollover, and the only reachable case is `"past"` after an empty read — the date became past between the two statements. It answers **404**, and a reload resolves it. That window is bounded by one round trip (single-digit milliseconds) and it can never hit a sitemap-advertised URL, because the sitemap is itself built from `listArchivedDays` under the same DB clock: a URL enters the sitemap only once the row is already returnable, at which point step 1 answers it and step 2 never runs. Every other ordering — classify-then-read, or `Promise.all` — has the same straddle *and* can 404 a date whose row was returnable, which is why this one is chosen.

**Export accounting for the classifier**, against the real pins: `T-DB-9a` (`packages/db/test/published.test.ts:702-710`) 4 → **8**, `T-DB-9b` (`:712-724`) 8 → **12**, `T-DB-S5` 34 → **38** *(step-7 F1: was 35 → 39; PR 1 adds no export, so S5 enters PR 2 at its landed 34)* — all in PR 2, all in the same commit as the exports (§4.4). `T-DB-9c` is untouched: nothing is added to `/publishing`, and `todaySaoPaulo` does **not** move to the root barrel.

**Why it resolves at all.** Revision 1 404'd today's date and justified it as "surface with no consumer". The consumer is #34, whose acceptance criterion is *"Shared links land on the exact day/game page"* — and `/termo` is not a per-day URL: a link shared at 21:00 serves a different puzzle after the rollover. Sharing happens immediately after playing, which is exactly the window revision 1 left without a permalink. So the plan's own claim that #34 inherits "a stable per-day-per-game URL" was true only for yesterday and earlier. It is true for every day now.

**307, not 308, and this is not a nitpick.** A 308 is *permanent* and both browsers and intermediaries are entitled to cache it forever against that URL. `/arquivo/2026-08-14/termo` redirects to `/termo` today and must render the archived board tomorrow — a cached permanent redirect would break exactly the shared link this decision exists to serve, and would break it silently, days later, only for the people who followed it once. `redirect()` from `next/navigation` in a server component issues a temporary redirect, which is the correct semantics for a rule whose truth value changes at midnight. (This overrules the step-4 brief's "308"; the brief's substance — that today's URL must resolve — is what is implemented.)

**D4's on-time impossibility is untouched.** The redirect lands the player on the daily route, so a completion written from there is a normal daily write with `body.date === today` and derives `on_time = true` correctly. **No write ever originates from an archive path**, which is what the impossibility argument actually needs; `getArchivedDaily` still refuses today by SQL, and no archive page ever renders today's content.

**No SEO cost.** The daily play routes are not an SEO surface (ADR-0028 `:28-30`) and are absent from the sitemap; the redirect target is a literal from `routes`, so there is no open-redirect surface. `generateMetadata` on a redirecting request is never rendered.

### D1b — There IS a `/arquivo/<data>` day page, and it is what makes the month page legible on a phone (Q1, revised)

**Decision:** `app/arquivo/[data]/page.tsx` ships. It renders the games that date actually holds — one link each — plus a link up to its month.

**Why.** Three reasons, in order of weight. (1) **The AC says so**: *"Archive index and **day pages** designed against the design system"*. Revision 1 had no day page and did not record the absence as a decision. (2) It **fixes the month page at 390×844**: with a day page, a month row is one date link instead of four accent-marked game links, so a 31-day month is ~31 touch targets and ~1,400px of scroll instead of 124 anchors and ~2,800px of near-identical scroll. **The accent-density half of revision 2's argument is withdrawn (N14):** §7.5's row anatomy still carries up to four accent-marked game *names* inside the single row, so the number of accent marks per row is unchanged — what changes is that they stop being four competing destinations and become one target's contents. ### D2 — Every archive route is `force-dynamic`; ADR-0014's "cacheable" is amended, and the contradiction with the ISSUE is surfaced to Fernando (Q2)

**Decision:** `export const dynamic = "force-dynamic"` on all seven pages, on `sitemap.ts` and on `robots.ts`. No `revalidate`, no `generateStaticParams`, no `fetch` on any server path — ADR-0028 D4's posture, copied verbatim, and ADR-0028 D6's standing prohibition obeyed rather than argued with.

**The argument, which is not the daily's argument.** The daily is `force-dynamic` because a cached page serves yesterday's puzzle after the rollover. An archived day's *content* is immutable, so that reason does not transfer — and pretending it does would be dishonest. The real reason is the kill switch: ADR-0010 `:23` and ADR-0024 `:59-61` make `killed_at` the operator's takedown, it is a **database write with no deploy and no invalidation hook**, and a cached archive page outlives it for the whole TTL.

**The trade, engaged honestly rather than by strawman.** Revision 1 dismissed the whole class of caching with *"a takedown that takes effect 'within an hour' is not a takedown"*. Nothing forces an hour. `export const revalidate = 60` bounds takedown latency to **sixty seconds** while cutting crawler-driven database reads on the archive's own pages by roughly two orders of magnitude — and the archive is a surface ADR-0005 `:13` makes an organic-search asset, i.e. one whose latency is a product property, not only a cost one. The honest statement of the choice is therefore: **sixty seconds of takedown latency, against per-request database reads on the crawler-facing surface**. This plan takes the zero-latency side because the archive has no traffic yet (so the cost side of the trade is currently zero), because an operator takedown is the one archive operation with a legal or reputational clock on it, and because the cheap fix makes the trade disappear entirely rather than splitting it.

**That cheap fix is the standing precondition, and it is recorded, not gestured at.** Any future caching of an archive route requires, *first*, that the `killed_at` write gain a writer that calls `revalidatePath` for the affected paths (the day page, the month page, the index, the play page, the sitemap). Cache-then-invalidate is the wrong order and this plan says so on the record; ADR-0053 carries it as the condition on any future `revalidate` in this family.

**So ADR-0014 `:15` is amended.** The archive is that clause's *own named example* of a cacheable read, and it is shipping uncached. The honest record is: the scope edge is `public, unauthenticated, non-user-specific, helper-gated` — **cacheability was never the load-bearing property**, it was a description of the case ADR-0014's author had in mind. ADR-0028 already extended the same clause once for the play routes; #31 extends it for the archive.

**And the ISSUE is contradicted, which is a separate obligation.** Issue #31 says verbatim: *"These are public, unauthenticated, **cacheable** pages."* CLAUDE.md requires a contradiction between a plan and a ticket to be surfaced to Fernando rather than silently resolved. It is **flag F1**, in his words, with the sixty-second number in it.

**Revisit trigger, with something that can observe it.** The trigger is Neon compute-hours attributable to archive/bot traffic, read off the Neon console — observable today, with no instrumentation, which is the point (a trigger nobody can observe never fires). p95 on `/arquivo` is the better metric and **#37 owns instrumenting it**; until #37 the console figure is the one this plan commits to.

### D4 — Three new readers in `published.ts`, over ONE spelling of the publication conjuncts (Q4)

**Decision:** `packages/db/src/published.ts` gains **two** private helpers, one private predicate, three exported readers and one exported clock classifier.

```ts
/**
 * The publication conjuncts, and the ONLY spelling of them (ADR-0010 :20,
 * ADR-0014 :16). Both predicates below spread this; neither re-types it.
 * ADR-0026 :92-95 protects the wall's SEMANTICS from acquiring a write-side
 * bound — it is not a rule against factoring the conjuncts a reader shares.
 */
function publishedConjuncts(): readonly SQL[] {
  return [
    sql`${dailyPuzzles.publishedAt} <= now()`,
    isNull(dailyPuzzles.killedAt),
  ];
}

/**
 * The DB clock's São Paulo day, and the ONLY spelling of it in this module.
 * `wallPredicate`'s today branch, `archivedWallPredicate`'s past bound and
 * `archiveDateClass` all interpolate this one fragment; a second timezone
 * cast of the clock anywhere in this file is the divergence T-DB-S53(b)
 * reds on.
 *
 * The wording avoids the scanned phrase deliberately (IN-3): T-DB-S53(b)
 * counts occurrences in the source, so a doc block quoting the expression
 * would make the scan count its own comment. The scan additionally strips
 * comments before counting, so this is belt and braces.
 */
function saoPauloToday(): SQL {
  return sql`(now() at time zone ${SAO_PAULO_TIME_ZONE})::date`;
}

/** UNCHANGED BEHAVIOUR. Same signature, same required `game`, same
 *  "date omitted means the DB clock's SP day". Only the two publication
 *  conjuncts are now spread instead of re-typed. */
function wallPredicate(game: Game, date?: string): SQL | undefined;

/**
 * The ARCHIVE wall: the same conjuncts plus "strictly before the DB
 * clock's São Paulo day". Today's daily is not archive content — it has
 * its own route (D1a redirects to it), and no write ever originates from
 * an archive path. The date bound here is a READ bound on new readers;
 * ADR-0026 decision 6's rule that the WRITE bound lives in the route and
 * not in SQL is untouched.
 */
function archivedWallPredicate(game?: Game, date?: string): SQL | undefined;

/**
 * Which side of the DB clock's São Paulo day a date falls on. Reads no
 * table and carries no wall — it answers a question ABOUT the clock, and
 * `apps/web` needs it only to tell "today, redirect" from "absent, 404"
 * after a walled read has already come back empty (decision 1a).
 */
export async function archiveDateClass(
  db: Db, date: string,
): Promise<"past" | "today" | "future">;
```

**Why the extraction, and why revision 1's refusal was wrong.** `wallPredicate` takes `game` as **required** and treats `date === undefined` as *equals today* — the exact opposite of the archive's need — so the new readers genuinely cannot call it. Revision 1 concluded from that that the archive should re-type `published_at <= now()` and `killed_at IS NULL`, and pinned `wallPredicate` as "byte-identical" to make the refusal a rule. That ships a **second spelling of ADR-0004's wall**, against ADR-0010 `:20` (*"through **one shared query helper**, not a predicate re-typed per route"*, with the archive named in that very sentence), against ADR-0014 `:16` (*"otherwise ADR-0004's guarantee would have two enforcement points to keep honest"*), and against the argument revision 1 itself makes one paragraph earlier when it refuses a `date < today` check in the page. ADR-0026 `:92-95` protects the wall from acquiring the *write* bound; it says nothing about factoring out a conjunct two predicates share, and reading it as a no-touch rule was the error.

**`wallPredicate`'s behaviour comes out byte-identical**, which is what ADR-0026 `:92-95` actually protects, and T-DB-S53 pins **both halves**: (a) the three shipped readers still return today's, dated and future-relative rows exactly as before over the same seeds; (b) **one spelling, asserted by a source scan over `packages/db/src/published.ts` with comments stripped first** — `publishedAt` appears in exactly one comparison, `killedAt` in exactly one `isNull`, and `now() at time zone` exactly once, so a second copy of any of the three reds the suite. **Comment-stripping is load-bearing, not hygiene (IN-3):** without it any doc block that quotes the expression — including the one D4 proposes above — makes the scan count two and red on its own comment.

**Why a source scan and not a structural comparison of the predicates (N6).** Revision 2 claimed the conjuncts would be "asserted structurally, so a future divergence in the **copy** reds here", and that claim was unimplementable under this plan's own pins: `publishedConjuncts`, `wallPredicate` and `archivedWallPredicate` are module-private, so no test can import them, and exporting one to compare `.toSQL()` fragments would red T-DB-9a — the tripwire whose entire purpose is that the module's surface is exactly the audited set. What remains available to a test is behaviour, which catches a *semantic* divergence but not a duplicated copy that still behaves the same. The source scan does catch it, needs no export, moves no tripwire, and is the register the plan already uses twice (T-WEB-S166's `/arquivo`-literal scan and T-LINT-S37's import scan). The claim is now exactly as strong as its mechanism.

- **`getArchivedDaily<G extends ProjectedGame>(db, game, date)`** → `Extract<DailyPuzzleResponse, {game: G}> | undefined`. `getPublishedDaily`'s twin with the extra conjunct, same `ProjectedGame` bound for the same compile-time reason (`published.ts:56-69`), same `stripDailyContent` inside the wall. **Why a fourth reader instead of a `date < today` check in the page:** the check would be a second enforcement point for ADR-0004's guarantee — the thing ADR-0014 `:16` exists to prevent — and it would need the page to fetch the DB day separately, which is a second round-trip and a second place to get the timezone wrong.
  **It never throws on a bad row.** If `stripDailyContent` rejects a historical row's content, `getArchivedDaily` logs `console.error` with game and date and returns `undefined`, so the page 404s. This is C12's decision, taken here rather than deferred: the URL is one the plan's own sitemap advertises to Google, and a 500 on it is worse than a 404 in every dimension — it is not cacheable-negative for a crawler, it pages nobody, and it hides which row is bad. The log line *is* the alarm. The behaviour is scoped to this reader; `getTodayDaily` and `getPublishedDaily` keep throwing, because on those a bad row is a live incident. T-DB-S55 seeds a malformed row and pins `undefined` + the log.

**The tripwires move in the same commit as the exports** (the shipped law, plan 035's accounting style), and §4.4 states the arithmetic **per commit**, because pre-commit runs the full suite at every commit (N13): `T-DB-9a` 4 → **8** and `T-DB-9b` 8 → **12** in PR 2; `T-DB-9e` (the **user entry**, `packages/db/test/user.test.ts:100-118`) **unchanged at 15**, and `T-DB-S5` **unchanged at 34 through PR 1** and **34 → 38** in PR 2 *(**step-7 F1:** this sentence read "9e 15 → 16 in PR 1; S5 34 → 35 in PR 1 and 35 → 39 in PR 2". ### D4a — NO migration and NO index; the read-cost posture is bounded readers plus `prefetch={false}` (revised, N11/N-AUDIT)

**Decision:** `packages/db/src/schema.ts` and `packages/db/migrations/**` are untouched. Revision 2's `daily_puzzles_date_idx` on `(date)` is **dropped**, and §1's original "no schema change, no migration" posture is restored.

**Why the index went, on the merits and not on cost alone.** A `(date)`-only btree does not serve either new reader's predicate. Both readers carry `published_at <= now()` **and** `killed_at IS NULL`, neither of which is in the index, so every candidate row is still a heap fetch — which is the exact cost revision 2 justified the index by ("a sequential scan reads the whole table's main heap", because rows carry a `jsonb content`). `listArchivedMonths` is a `SELECT DISTINCT` over every published row and gains nothing at all; `listArchivedDays` gains ordering and early `LIMIT` termination and nothing else. An index that would actually pay — `(date DESC, game) WHERE killed_at IS NULL`, or a covering index over the published conjuncts — is a larger design decision than a routing ticket should be making, and it would be the repo's **first index-only migration**, firing the napkin's apply-before-push ritual and adding a hand-applied Neon step to the critical path of a two-PR ticket.

**And nothing needs it yet.** `daily_puzzles` grows at 4 rows/day — **1,460 a year**. The readers run on `force-dynamic` pages with, today, no traffic. A sequential scan of a few thousand rows is not a problem this plan can honestly claim to be solving.

**ADR-0040 consequence (g) is therefore not falsified, and that is a decision, not an omission.** `docs/adr/0040-…md:254-259` states: *"**No index is owed on `daily_puzzles`, which has none beyond its primary key** (`packages/db/src/schema.ts:110`). **Revisit only if a second game needs a content read-back, or if `daily_puzzles` exceeds ~10⁵ rows.**"* Both halves survive #31, verified against the shipped readers:

- The factual half stays **literally true** — the table still has no index beyond its primary key after this ticket.
- Trigger one, *a second game needing a content read-back*, does **not** fire. `listArchivedDays` and `listArchivedMonths` name no `content` column at all (§4.2, and T-DB-S54 asserts it on the returned key sets), and `getArchivedDaily` reads content for exactly one `(game, date)` — served by the composite primary key, which is what "read-back" in (g) was never about (it names `listUsedTermoAnswers`' ~400-row scan).
- Trigger two, ~10⁵ rows, is **~68 years** away at 4 rows/day.

`0040:157-158`'s costing of the rejected partial-unique index partly on *"it would be `daily_puzzles`' first index beyond the primary key"* also stays true for the same reason. **ADR-0040 is not amended by this ticket**, and D19 records it in the explicitly-NOT-amended list with that reasoning rather than leaving it absent — the shape #30 was caught on at step 6 was an ADR nobody looked at, not an ADR ruled on and cleared.

**The revisit trigger this plan does own.** If archive read latency on `/arquivo` ever becomes the thing D2's revisit fires on, an index is the **second** response, after `revalidate` — and its shape is decided against the real predicates then, with `EXPLAIN` output, not by pattern-matching "table scan → add index". ADR-0053 records that ordering.

**What replaces the index as this ticket's read-cost answer.** `listArchivedDays` is bounded on every page that is not the sitemap (`limit: 32` on the index, a month's edges on a month page, one date on a day page — D5), `listArchivedMonths` is one grouped scan rather than an unbounded row read, and D2's revisit trigger is observable on the Neon console today. That is the honest cost posture; an index would have been a guess dressed as one.

**Prefetch posture, stated where a reviewer looks for it.** Archive day and game links carry `prefetch={false}`. A month page holds up to 31 `<Link>`s into a `force-dynamic` route family and a day page four more; Next's default viewport prefetch would turn one page view into dozens of RSC requests against uncached, database-reading routes — the exact multiplier that would fire D2's own revisit trigger, produced by the framework rather than by traffic. ADR-0004 is not at stake (no archive link can address a future date by construction — the hrefs come from the walled readers), which is why this is a cost decision and not a wall decision.

### D5 — Month pages and day pages are the pagination; every page is bounded by construction (Q5)

**Decision:** ADR-0005 `:35` demands "real routing and pagination from early on". The pagination is the month page plus the day page, and there is no other. Payload arithmetic, restated for D1b's shape so it is checkable rather than asserted:

- `/arquivo`: 7 day-row anchors + one anchor per archived month. Months accrue at **12 rows/year**; at ten years the index is 127 anchors. It cannot grow into ADR-0051 D3's 2,000-DOM-element trigger this decade.
- `/arquivo/mes/<YYYY-MM>`: ≤ 31 day-row anchors + 2 month anchors = **≤ 33**, permanently. A month is a month. (Revision 1's shape was ≤ 124 anchors; D1b's day page is what removed the other 91.)
- `/arquivo/<YYYY-MM-DD>`: ≤ 4 game anchors + 1 month anchor = **≤ 5**.
- `sitemap.ts`: 1 day URL + ≤ 4 play URLs per date = **≤ 5 URLs/day**. The 50,000-URL sitemap limit is reached at **~27 years**; the read behind it is `listArchivedDays()` unbounded, ~4,400 rows at three years.

**Recorded triggers (the ADR-0051 D3 register, restated for this surface), each with the thing that observes it:** when `listArchivedDays()` for the sitemap exceeds **~10,000 rows**, or the sitemap body exceeds **1 MB**, the sitemap gets a sitemap *index* with per-year children — a new file, not a field change. Both are observable with one command against production (`curl -s <origin>/sitemap.xml | grep -c '<url>'` and `curl -sI`'s content length); no instrumentation is owed and none is deferred. The latency trigger (crawl latency on `/arquivo` dominated by the month query) is the one that needs #37, and D2 names the console-readable stand-in until then.

The calendar's grouping helper is **not** reused as the substrate: it is a client-side month grid keyed on a user's own history, and the archive's is a server-rendered link list keyed on publication — one shape, two meanings, and merging them would couple a public page to `/estatisticas`' payload contract.

### D6 — `generateMetadata` + self-canonical on every archive route; a request-time `sitemap.ts` and a `robots.ts` (Q6)

**Decision:**

- Every one of the seven pages exports `generateMetadata` returning a pt-BR `title`/`description` composed from `messages.archive` (ADR-0018 — no literal in a component, and no string built inside the metadata function either: the composers live in `messages.ts`, written out in §7.6) and `alternates: { canonical: <its own path> }`. Canonicals are self-referential and there is exactly one URL per resource. **Titles and descriptions are distinct across every `(date)` and `(date, game)`** — they carry the formatted date and, on a play page, the game name — which is what stops ~5 near-identical board pages per day from being thin duplicates. T-WEB-S173 asserts the uniqueness, not only the composition.
- `app/sitemap.ts` — `force-dynamic`, enumerating `/`, `/arquivo`, every month page, **every archived date's day page**, every `(date, game)` archive play page, `/modo-livre` + its three, `/privacidade`. **Excluded:** `/vincular` (already `robots: noindex`), `/estatisticas` (personal), the four daily play routes and their `concluido` siblings (ADR-0028 `:28-30` states outright that they are not an SEO surface).
- `app/robots.ts` — allow all, `disallow: ["/vincular"]`, `sitemap: <metadataBase>/sitemap.xml`.

**The crawl posture, stated because absence from a sitemap is not `noindex`.** This is the repo's first site-wide `robots.ts` and it sets one rule for everything: crawlable except `/vincular`. `/estatisticas` and the daily play routes are therefore **crawlable but unlisted** — they are simply not an SEO surface worth a sitemap slot, not secrets. That is safe: `/estatisticas` is a static shell whose aggregates arrive client-side behind `requireUserId`, so an anonymous crawler sees the zero state and nothing personal; the daily play routes render today's public puzzle. If Fernando wants either genuinely out of the index, the instrument is `robots: { index: false }` in that route's own metadata, not the sitemap.

**ADR-0004 compliance is structural, not procedural:** the sitemap's only source is `listArchivedDays()`, which carries the wall *and* `date < SP-today` in SQL. A future-dated URL is not filtered out of the sitemap — it is never produced. ADR-0028 D6 is untouched because a request-time `sitemap.ts` is not a build-time params array; D6's actual prohibition (`generateStaticParams`) appears nowhere in the diff, which §13 makes a grep.

**`metadataBase` is a step-5 verification, not an assumption:** the root layout sets one; the sitemap and the canonicals must resolve against the same value, and the implementer pastes the resolved absolute URL of one archive page from a preview deployment into the PR body. ADR-0013 `:36` — nothing hardcodes the apex outside environment config — binds here.

### D6a — ONE `parseArchiveParams`, called by `generateMetadata` AND the page (new, D-F4)

**Decision:** `apps/web/src/archive/parse-params.ts` exports the segment parsers, and **both** `generateMetadata` and the page body call them. On failure, `generateMetadata` returns minimal metadata with `robots: { index: false }` and **no `alternates`**, and the page calls `notFound()`.

**Why this is a real hole and not a shape quibble.** Revision 1 assigned validation to the page body only. In the App Router `generateMetadata` and the page resolve **independently** — a `notFound()` in the page does not stop the metadata function from having already composed a canonical out of the raw segment. On `/arquivo/mes/<hostile>` that canonical is built from attacker-controlled text, and a value beginning `//` or `https://` resolves against `metadataBase` to an **off-site absolute URL**: canonical poisoning, on the one surface in the product whose entire purpose is being indexed. The month-name composer additionally reflects the string into an indexable `<title>` (React-escaped, so not XSS, but indexable).

Explicitly *not* wrong, and not re-litigated: both anchoring regexes are safe in JS (`$` does not match before a trailing newline, unlike Python); `calendarDateString` round-trips through UTC and rejects `2026-02-30` (`packages/core/src/contracts/daily.ts:96-103`); range bounds reach SQL as `date` parameters; no raw segment reaches SQL. **The hole was ordering, not shape** — which is why the fix is one shared parser and not a new validator.

T-WEB-S173 carries a hostile-segment case asserting the canonical is same-origin or absent, and that `robots.index` is false on the failure branch.

### D8 — The write window's lower bound is removed; the calendar's clamp keeps its own constant (Q8)

**Decision:** `ACCEPTED_DAYS_BACK` is deleted and replaced, in the same module (`apps/api/src/publishing/dates.ts` — ADR-0026 D6's layer, unmoved), by two things with one owner each:

```ts
/**
 * The rollover slack: the only days a write INTENDED AS ON TIME may
 * legitimately predate the account's birth day (a 00:30 account flushing
 * yesterday's completion). Its ONE consumer is the stats calendar's range
 * clamp — `computeCalendar(rows, since, today, rolloverSlackDays)`. It is
 * NOT the write bound, it never was the same idea, and it must never be
 * used as one again: #31 widened the write window to the whole archive
 * (ADR-0053), and a clamp that followed it would drag the calendar's
 * range back arbitrarily and paint "missed" over days the account did not
 * exist for — the exact failure ADR-0051's Rejected list names at :175-178.
 */
export const ROLLOVER_SLACK_DAYS = 1;

/**
 * The write window (ADR-0026 decision 6 as amended by ADR-0053).
 * UPPER bound only: a completion or a guess may target any day up to and
 * including the DB clock's São Paulo today. The LOWER bound is GONE — the
 * archive is every published past day, and the WALL is the only authority
 * on which those are. Bounded in the ROUTE, never in SQL: decision 6's
 * layer rule is unchanged, and `wallPredicate` is untouched. The volume
 * ceiling this removal owes lives in the completion route (ADR-0053
 * decision 13), not here: it is a rate rule, not a date rule.
 */
export function isWritableDate(date: string, today: string): boolean {
  return date <= today;
}
```

**Why the lower bound can go — the argument, rewritten, because revision 1's was false.** Revision 1 argued *"forging the past **is** solving the past"*. That is untrue, and the codebase says so in its own words.

- **For Termo it is false outright.** ADR-0038 D9 `:197-206` records that the guess route **IS an answer oracle** and that *"its real cost is ONE authenticated request"*: six dictionary words that are not the answer make a terminal board, `status` is `"lost"`, and decision 2's refine then **requires** `answer` in the response. The exploit is therefore **two requests per archived Termo day and zero solving** — mint a session (unthrottled, `attach/service.ts:49`), `POST /termo/guess` with six arbitrary words, read `answer`, `POST /completions` with it, and `judgeTermo` returns `"won"`. Both routes share one window (§6), so removing the lower bound widens the oracle's date axis exactly as far as the write window.
- **For the three grid games it is only marginally better.** ADR-0038 `:216-219` records the comparison the project already accepted: *"`solveBinairo(givens)` is a 0.04–0.16 ms **local** solve over data the published payload hands the client (ADR-0027 decision 1), needing no session, no network and no server."* The solvers ship in the client bundle. Forging a grid day costs one public read plus a fraction of a millisecond of CPU, not human effort.

**So the honest argument is about what forgery BUYS, and it is not nothing.** What a forged past win **cannot** reach, verified: the streak (ADR-0008 rule 1, `streak.ts` consumes `onTime` as row data), any time statistic (`stats.ts:295`'s `countsOnTimeWon` filter), Termo buckets 1–6 (`stats.ts:316`), the `termoGuessWins` medals (`derive.ts:119`'s explicit `countsOnTimeWon`), Dia Perfeito (`perfectDays` returns at `stats.ts:156` on `!countsOnTimeWon`), and the calendar's `onTime` state. What it **can** reach, and revision 1 asserted a clean "nothing pays" over:

- **`solved` totals.** `stats.ts:273` (`gameRows.filter((row) => row.outcome === "won").length`) and `:327` (the Termo twin) carry **no `onTime` conjunct** — by ADR-0051 D6's explicit decision, and the code comment at `:270-272` says why.
- **Ten of the twenty-three medals.** `medals/derive.ts:32-34` defines `countsAnyWon = countsOnTimeWon(row) || countsLateWon(row)`; it backs `totalWins` (`:100-106`) and `eachGameWon` (`:124-127`), reaching **`first-win`, `wins-10`, `wins-50`, `wins-100`, `wins-500`, `binairo-30`, `sudoku-30`, `nonogram-30`, `termo-30`, `all-games`** (`definitions.ts:52-65, 95`). 125 archived days × 4 games = 500 late wins mints every volume medal in the catalog.

**It is accepted, on the record's own terms, and the reason is quoted rather than paraphrased.** ADR-0006 `:51`: *"It is not an anti-cheat system, and no detection infrastructure is being built for a rank that v1 does not have."* ADR-0004 `:13`: *"There is nothing to cheat for — v1 has no global ranking (a product veto), so a cheated streak only cheats its owner."* And the decisive point: **legitimately solving 500 archived puzzles is exactly what #31 ships**, and ADR-0052 D3's volume class was designed to count late wins (`definitions.ts:50-51`'s own comment: *"late wins included — a late solve is honestly a…"*). The derived medals cannot distinguish a scripted mint from a determined player *by design*, not by oversight. ADR-0053 decision 5 carries this version, not revision 1's.

**Rejected alternatives.** *A widened-but-finite window (365 days):* contradicts AC 1's "every published past day" the moment the archive is older than the window, and picks a number nothing measures. *The archive floor as the bound:* it is `listArchivedMonths`' last element, so the route would run an extra query per write to compute a bound the wall already enforces. *Splitting the two write routes:* ADR-0038 D8 hoisted the bound precisely so they cannot drift, and an archived Termo needs both windows to agree or it is unfinishable.

**And it tightens the future edge, which is worth claiming in the PR.** Today neither write route bounds the future in the route at all — a future date is refused *at the wall*. `isWritableDate`'s `date <= today` adds a route-level future refusal **ahead of** the wall read. T-API-S98 therefore describes **new** behaviour ("still 404, and now rejected in the route before the wall read"), not preserved behaviour, and is worded that way (B12).

### D8a — The removed bound is replaced by a real ceiling: 50 LATE completions per user per São Paulo day (new, D-F3) *(step-7 F16: the heading said "archive completions")*

**Decision:** `POST /completions` refuses a **late** write — one whose `body.date` is strictly before the DB clock's São Paulo today — with `429 archive-cap` once the caller already holds 50 late completions written on the current São Paulo day. The check runs **after** the idempotent short-circuit, **after** `isWritableDate`, **after the wall read and after the judge**, and **only on the late branch**, so the daily path pays no extra round trip. *(**Step-7 F2 completes this sentence:** it named only the first two. Moving the ceiling to the write is half of what the fix bought — a request destined for a terminal 404 or 422 now never pays the count and never receives a retryable 429 where a terminal status is correct.)*

**Why a ceiling has to ship, and why revision 1 licensed the removal with the wrong ADR.** Revision 1 cited *ADR-0024 `:99-104`* — a section headed "Accepted for v1: no rate limiting on the **public reads**", about `GET /daily/<game>` and `GET /buffer-depth`. A read-side posture cannot license a write axis. The governing posture is **ADR-0026 `:170-181`**, which revision 1 quotes and then deletes the middle of: *"the composite PK caps rows at one per (user, game, date), **decision 6 caps the date axis at two days**, and each request costs one jsonb wall read plus one insert — so the only uncapped axis is minted-users × 2 days, with Vercel's platform firewall as the backstop."* D8 deletes that middle clause. Verified absent: no `middleware.ts` in either app, no firewall rules in either `vercel.json`, no rate-limit dependency anywhere, and `POST /session` mints unthrottled. Without a ceiling, max rows per minted identity goes from **8** to **4 × |archive|** — 4,380 at three years and growing by 4/day forever, at ≈5 neon-http round trips per row; 1,000 scripted identities against a three-year archive is ≈4.4M rows and ≈22M round trips from a laptop. Downstream, `listCompletionsForStreak` (`completions.ts:100-113`) is deliberately unfiltered and unlimited on the argument that *"the composite PK bounds the result at ≤4 rows per day"* — that bound survives, the **rate** does not, and `GET /streak`, `/stats` and `/medals` each read the whole set per request; `mergeAccounts` unions both sides in one statement; the `users` cascade means the LGPD delete path scales the same way.

**The mechanism, in full.** *(**Revised at step 7, finding F1+F2.** This plan specified a standalone counter the route called before the wall read. That shape is check-then-act — `Promise.all` over N requests reads one snapshot of the count in all N and writes N rows, so the bound held only against a sequential client — and it put the route's most expensive statement ahead of two cheap ones that could refuse the request outright. The counter is **gone**; the ceiling is a guard inside the insert, at the write itself. Nothing is exported from `packages/db` by PR 1 as a result: §4.4's arithmetic and §13's tripwire values move with it.)*

```ts
// packages/db/src/completions.ts — no new export. `recordCompletion` gains
// an OPTIONAL ceiling, supplied only on the late branch, and answers a
// discriminated result:
//   { capped: false; record; recorded } | { capped: true }
// With a ceiling the INSERT becomes ONE guarded statement —
//   insert into completions (…) select … where (select count(*) …) < max
//   on conflict do nothing returning …
// — so count and write cannot interleave. "Late" is still spelled ONCE, by
// negating onTimeSql() inside the guard (ADR-0026 decision 2's rule).
// Without a ceiling the statement and the return shape are byte-identical
// to what the daily ritual always had.
```

The route calls `isLateDate(body.date, today)` — a named predicate beside `isWritableDate`, so the route, the guard and PR 2's `archiveDateClass` converge on one meaning instead of three spellings — passes `{ day: today, max: ARCHIVE_WRITES_PER_DAY }` on the late branch only, logs `{ event: "archive-cap", userId, day }` and returns `errorResponse(429, "archive-cap")` when the result is `capped`. A capped caller can still **replay** a day it already holds: the guard suppresses the insert, the unconditional read-back still answers, and only "refused AND no row readable" is `capped`.

**Why 429 and why it composes with everything else.** `TERMINAL_STATUSES` in `apps/web/src/play/sync.ts:47` is `{400, 403, 404, 415, 422}` — **429 is not terminal**, so a capped write runs the bounded in-page ladder, then stays `pendingSync` and flushes on a later trigger. That is the *correct* semantics for a per-day rate cap: the record survives, and it lands after the next rollover. It also composes with D12a, because `prunePlayRecords` never deletes a `pendingSync` record. **No `sync.ts` edit, no `TERMINAL_STATUSES` edit, no client change, no wire-contract change** — `errorResponse(status, error)` is route-local (`completions/route.ts:50`) and the token is a plain string no contract parses.

**But the archive has to grow the UI for it, which revision 2 assumed it already had (N10).** "The player sees the existing pending line" was true of the *mechanism* and false of the *screen*: the pending line lives in `ConclusionView` (`messages.play.sync.pending`), and D14 plus T-WEB-S183 keep `ConclusionView` out of the archive's module graph entirely. Revision 2's §7.4 anatomy listed an outcome, a note, no time and two links — **no pending state at all** — so a capped completion would have rendered as a finished result with nothing saying it was not recorded. §7.4 now carries the pending state, §7.6 gives it its own string (the archive's cause is a rate cap, not connectivity, so the shipped *"sincroniza quando a conexão voltar"* would be wrong), and T-WEB-S177/S178 assert it.

**Where 50 comes from, named honestly.** It is **not measured — there is no traffic to measure**, and saying otherwise would be the kind of borrowed number this repo rejects. It is chosen as: comfortably above the largest plausible human archive session (a player clearing a full week of all four games is 28), and two orders of magnitude below the 4,380 an uncapped three-year archive allows one identity. **[Fernando-adjustable — flag F8.]**

**And the cap is its own instrument.** The revisit trigger for D8's abuse posture is now observable rather than aspirational: **the first `429 archive-cap` in the logs is the measurement**, and it distinguishes the two cases it needs to (a legitimate marathon player trips it once; a script trips it on every minted identity). The second trigger stands: the first month in which archive completion writes exceed daily completion writes by an order of magnitude. ADR-0053 decision 13 records both, and §14 carries write amplification as a watch item — which revision 1's eight items omitted entirely.

**The guess route gets no ceiling, and that is a decision, not an oversight.** It writes nothing, allocates nothing unbounded (≤6 elements of `^[a-z]{5}$`) and was already unthrottled per-request before #31 — the date axis was never what bounded its request count. What #31 changes is the number of distinct days whose answer it will yield, which is precisely the exposure ADR-0038 D9 already disclaims and which is *less* objectionable after #31, because those days are now genuinely playable. What it does falsify is (f)'s *volume* claim, which is why ADR-0038 is amended (D19) rather than waved past.

### D9 — Pre-birth late completions are OFF-CALENDAR, with the aggregates carrying them (Q9)

**Decision:** ADR-0051 D2's obligation is discharged by its **second** named exit, verbatim: *"off-calendar with the aggregates carrying them"*. A late won row dated before the account's clamped range start emits **no calendar day entry** and still feeds the aggregates that count it. This requires **zero change to `computeCalendar`'s behaviour**, because ADR-0051 D2 `:79-80` already specifies it: *"Rows dated before `effectiveSince` emit no day entry but still feed every aggregate."* What makes it *true after the widening* is D8's constant split, and nothing else: `computeCalendar` bounds its range extension by `extensionFloorDay = sinceDay - acceptedDaysBack` (`stats.ts:223, 239-242`), so holding the clamp at 1 while the write window opens is what stops a far-past row from dragging the range back and painting fabricated `missed` days.

**Which aggregates, precisely — revision 1 got this wrong.** It said late rows feed *"`solved`, the medal volume rules, `perfectDays`' inputs"*. `perfectDays` **skips on `!countsOnTimeWon(row)` at the first line of its loop** (`stats.ts:153-158`), so a late row never reaches it; had the sentence been true it would have falsified ADR-0008 rule 2 and contradicted this plan's own T-API-S100. The correct statement: an off-calendar late won row is an **input to** `computeStats`, where the on-time conjuncts exclude it from every time statistic and from Termo buckets 1–6, and the only aggregates it moves are **`solved`** (`stats.ts:273`, `:327`) and the **ten volume medals** D8 enumerates (`medals/derive.ts:32-34`, sanity-checked against ADR-0052 D3's volume class, which counts late wins by decision).

**Why not a fourth `CalendarDayState`.** `calendarDayStateSchema` (`contracts/stats.ts:53`) is `z.enum([...])`, strict-parsed on both ends. Adding a member is a wire **value-set** growth: during a deploy skew, an already-loaded client parsing a payload containing the new state fails, the hook settles `null`, and the user's entire calendar disappears — indistinguishable from "no history". ADR-0052 D5 **names and designs against** exactly this shape for medal ids (its id text is a reasoned design choice — unknown id *values* parse and are silently dropped — and the only measured figure in D5 is the ~2 KB copy-bundle cost; ADR-0023 `:37-40` reserves "measured" and "prove" for the real thing, and this plan polices that vocabulary elsewhere, so it observes it here — N8). It also costs a legend row, an aria string, a CSS treatment and an ADR-0008 `:40` amendment, all to render days the account did not exist for.

**Why it is honest, not a dodge.** The stats calendar is *the account's own days* (ADR-0051 D2's first sentence). A day before the account existed is not one of its days. Meanwhile the *common* case — an account solving an archived day from inside its own lifetime — renders `"late"` through machinery that already ships end to end (`CalendarDayState`, the wire schema, the legend, the aria and the outlined-cell CSS at `app/estatisticas/page.module.css:469-477`). AC 3's "appears distinctly in the calendar" is satisfied by the case that actually happens.

**What is amended, and it is TWO ADRs, not one.**

- **ADR-0051 D2 `:75-79`** — *"The bound is **route-supplied**: `ACCEPTED_DAYS_BACK` lives at `apps/api/src/publishing/dates.ts` (ADR-0026 decision 6's layer) and `computeCalendar(rows, since, today, acceptedDaysBack)` takes it as a parameter — one constant, one owner."* Revision 1 recorded this as "two constants, two owners", which is **false**: the subject of "one constant, one owner" is the **calendar's** bound, and after the split that is `ROLLOVER_SLACK_DAYS` — still one constant, still one owner, and *more* true than before. What actually becomes false is the **identifier name** (the constant is gone) and the sentence's **coupling of the calendar's bound to ADR-0026 decision 6's layer**, which is now a different owner entirely. ADR-0051 **D5 `:134-136`** names the constant again (*"its `ACCEPTED_DAYS_BACK` must stay in the route layer"*) and is stale in the same way. Both decisions are annotated in place.
- **ADR-0008 rule 2 `:25`** — *"The stats calendar shows the date as solved with a visually distinct 'solved later' state."* For the pre-birth class this rule creates no calendar entry at all, so the sentence is simply false for it. Revision 1 dismissed ADR-0008 by answering only `:40`'s "three visual states", which does survive — a different sentence. **This class is created by #31 and by nothing else**: before #31 a won row can be at most one day back, always inside the extension floor (ADR-0051 `:81-83` says so). `CONTEXT.md:12`'s **Late completion** row carries the same claim ("shown distinctly in the calendar") and is qualified in the same commit.

**Mechanical teeth (AC 3's hardest half):** T-CORE-S80 pins that a late won row 400 days before `since` emits no day entry, does not move `days[0].date`, and still moves `solved`; T-API-S103 pins the same through the live `/stats/calendar` + `/stats` pair over PGlite. **[Fernando-adjustable — flag F3.]**

### D10 — The Termo fail row stays unqualified; ADR-0008 rule 3 is accepted as written, and AC 3 carries the carve-out in its own words (Q10)

**Decision:** `termoStats`' fail-row branch (`packages/core/src/stats.ts:307-315`) is **not touched**. A lost archive Termo counts in the fail row exactly as a lost daily Termo does.

**The argument is textual and it holds.** ADR-0008's verbs are disjoint: rule 2 excludes late **completions** from the distribution; rule 3 says a lost Termo is **played**, not completed, and *"the loss records in the Termo guess distribution as the fail row"*. ADR-0051 D4 `:120-123` already wrote this reading down and `stats.ts:309-314` carries it as a comment; `CONTEXT.md:13`'s **Played** row agrees. A late *win* still never enters buckets 1–6 (the `countsOnTimeWon` conjunct at `stats.ts:316`, untouched).

**But AC 3 as literally worded is not met on this branch, and the plan says so rather than claiming it is.** AC 3's words are *"demonstrably never changes streak, times or **distributions**"*. The fail row **is** part of the guess distribution, and it **will** move from archive play. Revision 1's exit criterion claimed AC 3 was demonstrated by T-API-S100 — a test whose own claim list deliberately omits the fail row. That is a criterion asserting something the plan concedes elsewhere is false. Fixed in three places: T-API-S100 asserts the fail row **does** move (documented behaviour, pinned, not an untested consequence); §13's AC-3 line carries the carve-out in its own words; and it goes to Fernando as **flag F4** phrased as *"AC 3 as written is not met on this branch; ADR-0008 rule 3 says it shouldn't be — confirm"*, not as a residual.

**The cost, recorded loudly rather than fixed.** After this PR, nothing in the data distinguishes a late loss from an on-time one on that branch. ### D12a — `prunePlayRecords` gains bounded retention, and this is a `src/play/` edit made in the plan rather than discovered at step 5 (new, B4)

**Decision:** `apps/web/src/play/play-record.ts`'s `prunePlayRecords(keepDate)` keeps the **50 most recent settled records dated before `keepDate`, ordered by `record.date` descending, ties broken by the record key** (so the order is total and the function stays deterministic), and deletes the rest. Everything else about the function is unchanged: `pendingSync` records are still never deleted at any date, a record that does not address its own key is still dropped whatever its date, and unparseable keys are still left alone.

**Fifty, not revision 2's twelve, and the ordering key is named (N3).** Twelve contradicted this plan's own sizing model: D8a caps archive *writes* at 50 because *"a player clearing a full week of all four games is 28"*, and 28 settled records against a retention of 12 means a player who cleared one week loses 16 of them on the first mount of any daily route (that mount makes `keepDate = today`, at which point every archive record is a prune candidate). One ticket, one model, one number: **50**, from the same sentence D8a's ceiling comes from, so retention and the write ceiling can never disagree about what a plausible session is.

**The ordering key is `record.date`, because it is the only orderable field the record has.** `playRecordSchema` (`play-record.ts:340-398`) carries no written-at timestamp, and adding one is a change to the local record contract in a file §1 restricts to this one function — out of scope, and a versioned-schema decision this ticket has no business making. So retention is "the 50 most recently **dated** archive results", not "the 50 most recently earned", and the consequence is stated rather than hidden: a player who already holds 50 settled archive records and then solves a date older than all of them loses that result on the next prune. D14 is re-argued against exactly that case rather than around it.

**Why revision 1's "safe, verified in the source" was materially wrong.** `play-record.ts:572-574` deletes when `!record.pendingSync && record.date < keepDate`, and `use-play-lifecycle.ts:116` calls it **unconditionally on every play mount with that mount's date**. Every archive record satisfies `record.date < today` **by construction** (D1: the archive is strictly past). So the moment an archive completion settles and the player reaches **any** daily route, the archive record is deleted. Revision 1's D14 gives the late-result panel *"two links out: the day's month page, and today's dailies"* — clicking the second one deletes the result the panel is showing, and Back then renders an empty playable board for a puzzle solved seconds earlier. Not "on a later day" as D12.1 worded it: on the **next navigation, in the same session**. Browsing the archive forward self-destructs the same way — `/arquivo/2026-05-01/sudoku` then `/arquivo/2026-06-01/sudoku` prunes the May record, because the second mount's `keepDate` is June.

**Why retention and not the two alternatives.** Making D15's revisit read from the server collides head-on with D15's "no new endpoint" and puts a per-request user-specific read on a crawler-facing route. Accepting it loudly would mean rewriting D12.1 and D15.3 with the real trigger **and** dropping D14's outbound link — but it would also take D14's own load-bearing sentence with it: D14 refuses the `/concluido` route because *"the archive play URL is itself permanent and re-renders the result from the local record on reload"*. If the record is gone by the next navigation, that sentence is false and D14 has to reopen. Retention is the only option that leaves the rest of the plan standing.

**The cap keeps the function's original purpose.** `prunePlayRecords` exists so localStorage does not grow without bound; a cap of 50 settled past records is still bounded, and it is 50 *records*, not 50 days. It is behaviour-neutral for the daily surfaces, because every daily read is keyed `(game, date)` on today's date and today's record is never a prune candidate (`record.date < keepDate` is false for it). **Step-5 duty:** measure the largest serialized record (a nonogram board) and paste `50 × that` into the PR body, so the localStorage ceiling is a number rather than an assumption. If `50 × largest` lands anywhere near a browser's per-origin quota the number moves and §14 records the deviation — that is the one thing that could reopen this decision, and it is a measurement, not a judgement.

`prunePlayRecords`' TSDoc gains the retention rule, its ordering key and its reason (#31), and T-WEB-S186 pins four properties: a settled past record survives a later daily mount; with 51 settled past records the oldest **by date** is the one deleted; a `pendingSync` record is never deleted whatever its date; an unsyncable-key record is still dropped whatever its date.

### D17 — CI scans `/arquivo` literally and DISCOVERS the date-bearing URLs from the app itself, safely (Q17)

**Decision:** `.github/workflows/impeccable.yml` gains `/arquivo` to the preflight path loop, a `data-page=` arm in its marker `case`, and `/arquivo` to both `detect` invocations. (The file holds **three** verbatim path lists — the preflight `for path in` loop and the two `detect` argument lists — plus one marker `case` of *patterns*; revision 1 said "four lists". The archive play URL needs no `case` arm: it falls through to the `data-play-state=` default, exactly as the `/modo-livre/<game>` paths do.) The month, day and play URLs are **not hardcoded**. The preflight step, which already fetches every path and already greps its body, discovers them:

1. after fetching `/arquivo`, extract the first `/arquivo/mes/[0-9]{4}-[0-9]{2}` **path**;
2. fetch that month page, assert 200 + `data-page=`, extract the first `/arquivo/[0-9]{4}-[0-9]{2}-[0-9]{2}` path, fetch it, assert 200 + `data-page=`;
3. from the day page extract the first `/arquivo/[0-9]{4}-[0-9]{2}-[0-9]{2}/(binairo|nonogram|sudoku|termo)` path, fetch it, assert 200 + `data-play-state=`.

**Why this shape and not the alternatives.** A hardcoded date **drifts** the moment production's archive edges move and 404s forever after. A date computed in the shell (`date -d yesterday`) is a *client clock* deciding what the São Paulo publication wall published — the one thing CLAUDE.md's invariant forbids. A stable alias route (`/arquivo/ultimo/...`) is a second URL for one resource. Discovery from the app's own HTML is drift-proof by construction, cannot 404 (the URLs came from a 200 body), and matches the **URL grammar**, not the markup, so a restyle cannot break it.

**The hardening, which revision 1 omitted and which is what makes it safe.**

- The preflight step gains an **`id:`**. Without one, `$GITHUB_OUTPUT` is unreadable downstream — revision 1's handoff could not have worked.
- **Paths only are exported, never full URLs and never anything carrying the bypass secret.** Each `detect` step composes `"$DEPLOYMENT_URL$ARCHIVE_MONTH_PATH?x-vercel-protection-bypass=$BYPASS&x-vercel-set-bypass-cookie=true"` itself. Exporting a query-string-bearing URL would put the secret in a step output, against the workflow's own rule that the body is only ever grepped, never echoed.
- Each extracted value is **re-validated against its anchored grammar before use** (`case "$p" in /arquivo/[0-9][0-9][0-9][0-9]-…) ;; *) fail ;; esac`), because the source is the deployment's own HTML.
- The values reach the `detect` steps through **`env:`**, never interpolated as `${{ steps.… }}` inside a `run:` string. Both `detect` steps are `run: >-` folded scalars, so a `${{ }}` interpolation would be textual substitution into a shell command fed from a fetched HTML body — an Actions expression-injection shape.
- Outputs are written with a **heredoc delimiter** (`{ echo "month_path<<EOF"; echo "$p"; echo EOF; } >> "$GITHUB_OUTPUT"`).
- The workflow's *"The body is only ever grepped, never echoed"* comment is amended in the same edit to say that a **path** may be echoed and a URL may not.

**The empty archive is a SKIP, not a red.** Revision 1 called an empty archive "the one honest failure mode". It is not: this workflow fires on **every preview deployment for every PR**, so until production has a strictly-past published day it would red on unrelated PRs and block the gate repo-wide. Discovery is therefore gated — if `/arquivo` yields no month link, the step prints a warning, exports empty paths, and both `detect` steps scan their fixed lists only. `/arquivo` itself is still asserted 200 + marker unconditionally, so the archive index can never silently disappear. Robustness with exactly one archived day is required and pinned by the grammar; multiline outputs are not needed.

## 4. `packages/db` — the archive readers, the shared conjuncts, the counter

### 4.1 One spelling of the publication conjuncts

`publishedConjuncts()` returns `[published_at <= now(), killed_at IS NULL]` as an array of `SQL` fragments, and `saoPauloToday()` returns the single `(now() at time zone 'America/Sao_Paulo')::date` fragment. `wallPredicate(game, date?)` spreads the conjuncts beside its `eq(game)` and its today-or-date branch (the today branch now interpolating `saoPauloToday()`); `archivedWallPredicate(game?, date?)` spreads them beside optional `eq(game)`, optional `eq(date)` and `date < saoPauloToday()`; `archiveDateClass` compares its parameter against `saoPauloToday()` and reads no table. Both predicates and both fragment helpers stay module-private, and T-DB-9a's four-name pin becoming an **eight**-name pin is entirely about the three new readers plus the classifier.

`wallPredicate`'s signature, semantics and every caller are unchanged: `game` stays required, `date === undefined` still means the DB clock's São Paulo day, and the three shipped readers behave identically over the same seeds (T-DB-S53, both halves). ## 7. `apps/web` — routes, screens, chrome, design and copy

### 7.1 Route files and their shapes

All seven are thin `force-dynamic` async server components in the `app/sudoku/page.tsx` register — a reader call plus a branch, with all composition in synchronous components tests render directly. Every one of them parses its params through `src/archive/parse-params.ts` (D6a) and exports a `generateMetadata` that calls the **same** parser.

- **`app/arquivo/page.tsx`** — `Promise.all([listArchivedDays(db, { limit: 32 }), listArchivedMonths(db)])`, one round-trip window. The 32 rows are grouped by date; **if exactly 32 came back the trailing date group is discarded** (it may be truncated mid-date), then the first seven groups render. That is the fix for the ragged-day arithmetic: `limit: 28` yields "the seven most recent days" only if every date holds all four games, and D3 establishes that the oldest dates do not — with a gap, 28 rows span eight dates and the last one silently truncates. Empty archive → the pt-BR empty state, still HTTP 200 with `data-page=` — the resource exists and is empty, which is not a 404.
- **`app/arquivo/mes/[mes]/page.tsx`** — `params.mes` is **parsed, never cast**: `z.string().regex(/^\d{4}-(0[1-9]|1[0-2])$/)` in `parse-params.ts`, then the month's first and last day are derived and handed to `listArchivedDays({ from, to })`, beside `listArchivedMonths(db)` for the previous/next links. A month with no archived day → `notFound()`.
- **`app/arquivo/[data]/page.tsx`** — `params.data` is validated with **`calendarDateString`** (`packages/core/src/contracts/daily.ts:96-103`), never a hand-rolled regex: it is the repo's one calendar-day validator and it rejects `2026-02-30`, which a shape regex accepts. Then, in D1a's order: `listArchivedDays({ from: date, to: date })` **first**; non-empty → render; empty → `archiveDateClass(db, date)`, `"today"` → `redirect(routes.home)`, anything else → `notFound()`.
- **`app/arquivo/[data]/<jogo>/page.tsx` ×4** — same date validation, same order: `getArchivedDaily(getDb(), "<jogo>", date)` **first**; a row → `<Archive<Jogo>Screen daily={daily}/>`; `undefined` → `archiveDateClass(db, date)`, `"today"` → `redirect(routes[jogo])`, `"past"` or `"future"` → `notFound()`.

**Read first, classify only on empty — the ordering is a decision, not an implementation detail (D1a, N2).** The archived path never runs the second statement, so the common case is one round trip; the redirect and 404 paths pay a second, which is the correct place to pay it. Classifying first would put a clock read on every archive render *and* would let the two statements straddle midnight in the direction that 404s a date whose row is already returnable. T-WEB-S171 asserts the order, not only the outcome: on a rendering path the classifier is never called.

**AC 1's "future days 404 through the predicate helper" is true twice over and by two different mechanisms:** the URL never validates as a real calendar day *or* the wall returns nothing — and the second is the one that matters, because a well-formed future date passes validation and is refused **in SQL, inside the wall**, exactly as the AC words it. T-WEB-S170 pins that a future date 404s with the reader mocked to its real behaviour, and T-DB-S46 pins that the reader is what refuses it.

**Props typing, decided rather than discovered (B11).** Every dynamic page hand-writes its props — `{ params: Promise<{ readonly data: string }> }` and `{ params: Promise<{ readonly mes: string }> }` — and **does not use `PageProps`**. `PageProps` is generated only into `.next/types`, `turbo.json`'s `"typecheck": { "dependsOn": ["^typecheck"] }` has no dependency on `build`, and the napkin requires `rm -rf apps/web/.next` before typecheck — so a `PageProps` reference makes `pnpm typecheck` fail with `TS2304: Cannot find name 'PageProps'` on a clean tree. Hand-written props survive the wipe and keep the documented gate order intact. (`ParamMap` in `.next/types/routes.d.ts` is all-`{}` today: these are the repo's first dynamic routes.) The `await params` landmine stands — §9's list keeps it.

### 7.4 The late-result panel

Renders when the shared status is closed. Anatomy:

- The outcome, in words, in `--ink` — won or lost, and, when the server's stored row is on-time (D15.3), the honest "você já tinha concluído no dia" reading instead of a late one.
- One line stating that the day is from the archive and moves no streak — the same fact D12b's `note` states during play, restated at the moment it matters.
- **A pending state, when the record is still `pendingSync` (N10).** Revision 2's anatomy had none, so a completion refused by D8a's `429 archive-cap` — or by any transient network failure — would have rendered as a finished result with nothing saying the server had not acknowledged it. The archive cannot borrow the shipped pending line: it lives in `ConclusionView`, which D14 and T-WEB-S183 keep out of the archive's module graph entirely, and its copy (*"sincroniza quando a conexão voltar"*) names the wrong cause for a rate cap. So the panel reads `record.pendingSync` — already on the local record it is rendering — and shows `messages.archive.result.pending` (§7.6), which is honest for both causes: the result is on this device and not yet registered. It never claims a registration that did not happen, which is `ConclusionView`'s own rule at `messages.ts:203-206` applied here. T-WEB-S177 asserts the pending render; T-WEB-S178 asserts that a settled `recorded` render never shows it.
- **No time, no streak, no day chips, no chaining CTA, no stats** (D11, D14).
- The game accent colours **shapes only** — the completion-stamp register (DESIGN.md `:39`: 3px circle in the game's accent, rotated −6deg, typographic content only). ADR-0041 D1 is absolute on words; D5's decorative exemption applies only because the outcome is already carried in `--ink` text beside the mark.
- **Accent text on the Termo archive route is categorically forbidden, not budgeted.** ADR-0041 D1 and DESIGN.md `:22` both record that mustard is **2.8501:1 on card, the ceiling over the whole paper family**, against a 4.5 floor — so no `color: var(--accent-termo)` on paper can ever satisfy the measurement, on any paper, at any size. Revision 1 framed accent text as a budgeted possibility with a measurement ladder; for Termo that ladder is arithmetically unreachable and framing it as possible invites an implementer to attempt it. For binairo, sudoku, nonogram and `--accent-app` the measured exception remains available on the ADR-0041 D1 terms (the ratio, the consequence (h) row, the `ALLOWED_ACCENT_TEXT` entry and its size pin), and any ratio that ships goes in the PR body.
- Two links out: the day's own page and the day's month page. **Not today's dailies** (D14).

### 7.5 The design — index, month, day and play chrome, at both viewports

AC 5 is *"Archive index and day pages designed against the design system"*, and `impeccable detect` is a floor, not a design. Every other screen in the repo ships far more specification than revision 1's single paragraph (`estatisticas/page.module.css` is 581 lines, `page.module.css` 469, `modo-livre/page.module.css` 243). This section is written in plan 033 §6.2's register: the anatomy is binding, the pixels inside it are the implementer's, against DESIGN.md and PRODUCT.md.

**Shared chrome, all four archive surfaces.** The `topBar` pattern every screen in this repo has (96 files reference `topBar`): a back affordance at the left, the wordmark centred, and — on the index, month and day pages — the archive's own kicker at the right. Back targets are one level up and never further: the play screen goes to its day page (D12b), the day page to its month page, the month page to `/arquivo`, the index to Hoje. On mobile the bar gains `min-height: var(--touch-target-min)` and the back link gains `padding: 10px 10px 10px 0`, the `/estatisticas` register (`page.module.css:516-522`). Title in Fraunces; the archive's lead sentence in `--ink-2` under it.

**The index (`/arquivo`).** One column at every width — a `max-width` measure centred on desk paper, not a two-column split, because the content is one list and a second column would be filler.

1. Top bar → title *Arquivo* → lead sentence.
2. **Recent days**, a section with a Fraunces sub-heading and **day rows, not a tile grid** — the anti-references ban the rounded-icon-tile idiom and a day row inside a card inside a section is exactly how card-inside-card happens, which is the other anti-reference. So: **the section is bare on desk paper, and the rows are hairline-separated** (the F5 stat-row register, `1px solid var(--line-soft)` between rows, none above the first or below the last). Each row is one `<Link>` to the day page and one touch target ≥44px: the date at the left in `var(--font-ui)` with `font-variant-numeric: tabular-nums` (ADR-0036 D1's exact case — a column of dates is a column of figures), and at the right the names of the games that date holds, in the kicker register, `--ink`, each carrying its game's accent as a **2px left rule** (a shape, ADR-0041 D1) and never as text colour. The row's accessible name is one composed sentence naming the date and the games (§7.6), so the accent rules never carry meaning alone (ADR-0041 D5).
3. **A short row renders fewer names and nothing else** — no placeholder, no greyed slot, no "3 de 4". A disabled-looking affordance would be fake navigation, which is the hub's own rule (`page.tsx:104-107`). A killed game produces exactly the same shape, which matters because the kill switch is D2's whole justification.
4. **Months**, a second section: one `<Link>` per month, newest first, in a wrapping row of kicker-register chips with `--line` borders (no accent — a month has no game). At 390px they wrap to a comfortable two or three per line; at 1440px to one line per year.
5. **Empty archive**: an honest pt-BR sentence in `--ink-2` where the sections would be, 200 with its marker, no skeleton and no fake rows.
6. **Rotation and washi**: the index gets **one** static rotation on nothing (it has no card) and **no washi tape** — tape marks a game, and the index is not a game. This is stated so the implementer does not add tape for texture; the archive's texture is the desk dot pattern and the hairlines.

**The month page (`/arquivo/mes/<YYYY-MM>`).** Identical row anatomy to the index's recent-days section — that is the point of having a day page — with the month name (`formatMonth`, already in `src/i18n/format.ts:57`) as the title, up to 31 rows, and previous/next month links as a pair of kicker-register links below the list, each absent when there is no such month. At 390×844 this is ~31 rows × ~48px ≈ 1,500px of scroll with one target per row; revision 1's four-links-per-row shape was ~2,800px with 124 targets and four competing accents per row.

**The day page (`/arquivo/<YYYY-MM-DD>`).** Title is the long-formatted date (Fraunces); below it, one **game card per game that date holds**, in the hub's Game-card register (card paper, 1px `--line` border, hard shadow in the game accent at 0.22, washi tape top-centre, kicker + Fraunces title) — this is the one archive surface where a card is right, because each card is a distinct destination with its own identity, and there are at most four of them. Static rotations ±0.3–2.4deg per DESIGN.md, alternating sign. At 1440px they sit in a two-column grid; at 390px they stack. Below the cards, one link up to the month.

**The play routes.** The daily's own screen, unchanged, plus D12b's **two** additions and **no new class**: the back affordance reads *← \<the long date\>* and targets the day page, reusing `screen.back`; and the not-counting note renders as a second `<p className={screen.rules}>` under the game's own rules line, already `--ink-2` (`screen.module.css:191-196`). **There is no mode chip** — the `modeTag` "register" revision 2 cited does not exist (free play puts a plain string into `screen.topDate`, which the archive needs for its date), and a sixth child of `screen.topBar` would require editing `apps/web/src/play/screen.module.css`, which §1 exception (iii) and §13's `git diff` criterion both forbid (N5). The board, keypad, timer and hint are byte-identical to the daily's, which is the whole point of D12.

**Stylesheet.** One new `app/arquivo/arquivo.module.css`, shared by index, month and day (the play routes reuse `screen.module.css` plus each game's shipped board sheet), plus `src/archive/late-result.module.css` for the panel. Both **use `var(--accent*)`, so both join `ink-on-accent.test.ts`'s `SHEETS` and its shared list in the same commit** — that suite is the whole automated ADR-0041 gate and an unlisted sheet is invisible to it.

**What CI can and cannot see, stated so the green is honest.** `impeccable detect` reaches the index, a month page, a day page and one play page in their **anonymous, never-played** state at both viewports — which is the real state for a first-time visitor, so unlike #30's medal section this gate is not vacuous. ## 10. Migration / deploy notes

**There is no migration (D4a).** Nothing is generated, nothing is applied to Neon, and the napkin's apply-before-push ritual does not fire on either branch. **Preview shares the production database** (handoff 019), which is exactly why not adding a hand-applied step here is worth something: an index applied by hand to a shared database is a step that can be forgotten between two PRs.

**Deploy ordering is a HARD REQUIREMENT, and revision 3 implements it as a PR split rather than as a promise (B3 → N4).** Revision 2 offered *"either the api change ships as its own PR first, **or** the two Vercel projects are confirmed deployed in that order"* and then put all seven commits on one branch and one PR — so the requirement was stated in §10 and not implemented by §12, which §14 item 2 conceded. The second arm was never actionable either: both projects deploy from the same push and web's deploy cannot be gated on api's.

**So the ticket ships as two pull requests:**

- **PR 1 — `feat/31-archive-write-window`.** `apps/api` (the constant split, `isWritableDate`, the ceiling, both write routes, the calendar route, the comments), `packages/core` (the rename and the doc block), `packages/db` (the ceiling folded into `recordCompletion`, no export — step-7 F1), the `/privacidade` line, and **all of §11's docs including ADR-0053 and its ten reciprocal lines** *(step-7 F5: nine became ten with ADR-0039)*. It is deployable, complete and reviewable alone: it opens the write window and changes no route. **No archive URL exists yet, so no player and no crawler can reach a page that would produce an archive write.**
- **PR 2 — `feat/31-archive`.** `packages/db`'s archive readers and classifier, all of `apps/web`'s routes and screens, the walls, the gates. Branched off `main` **after PR 1 is merged and its `apps/api` deployment is Ready**.

**The gate between them is a timestamp, not a sentence (§13).** PR 2's body carries the Vercel deployment id and Ready timestamp of PR 1's `apps/api` production deployment, and that timestamp is **earlier than PR 2's first commit**. A reviewer can check it without trusting anyone's account of the ordering, which is the whole point.

**Why this ordering and not the reverse.** `sync.ts:47`'s `TERMINAL_STATUSES` contains **404**; `sync.ts:244-249` logs *"it will not be retried"* and calls `settle(record, "rejected")`; `sync.ts:427-433` writes `pendingSync: false, syncOutcome: "rejected"`. In any window where web has the archive routes and api still refuses dates older than yesterday, **every archive completion is silently and irreversibly discarded** — and then, because the record is settled, `prunePlayRecords` is entitled to delete it. The split closes that window structurally, and it costs one extra PR.

(Revision 1 claimed there was no ordering requirement at all, on the grounds that a rejected archive completion "stays `pendingSync` and flushes on the next trigger". The `sync.ts` lines above are why that was false. It is also why D8a's `429` was chosen over a terminal status: a rate refusal must *not* be terminal, and 404 shows exactly what terminal means here.)

**Preview's archive is the real archive.** Nothing is seeded; nothing needs to be. That is what makes D17's discovery mechanism work, and it also means the preview's oldest archive day is production's — a one-to-three-game day for the first weeks (D3).

`.env` unchanged. No new dependency. No cron change. No migration. `metadataBase`'s resolved value is verified on PR 2's preview and pasted into its body (D6).
