4. **[2026-08-15] A vitest timeout sized off an ISOLATED local run under-shoots CI by 4-9x — and the ">10s locally" trigger excludes every test that actually flakes**

Trigger: over **40%** of the applicable budget (2s of `testTimeout` 5s, 4s of `hookTimeout` 10s; the hook half is unswept except PGlite's `createTestDb`, instrumented at #114 behind `MIOLOS_TEST_DB_TIMING=1`). **A bare local `pnpm test` is CAPPED at turbo concurrency 2 (#114), so it is never a "contended" anchor** — the uncapped command is `pnpm test --force --concurrency=10`, green on the 16 GB / 8-core box with #120's worker bound and a legal local anchor again, but **CI gate logs stay the preferred source**; no eligible anchor → record that as the reason the budget is not re-derived. Samples from a worker configuration nothing ships (pre-#120 `apps/web` at `cpus − 1`) are history, not anchors (ADR-0055 (o)); a capped run under-shoots CI and `turbo run test`. **Never size from a run in which anything timed out**: a killed test reports the wall, so that run's max is censored and turbo's sibling-kill biases the rest low. The anchor is a sample max, not a bound — a later session exceeding it is the estimator working, so **say so in the comment**: a recorded max owes an update only when a sample crosses the **trigger**, never on every new gate row, and a bare "max = N" goes stale on the next push (#109's own gate moved `T-WEB-S43` 944 → 990 ms mid-review; the next row came back at 666). Where a whole file shares one cost driver, budget the **file** (`vi.setConfig`), not whichever test runs first. **RTL's `waitFor` carries its OWN 1000 ms default, invisible to every rule above** — `vi.setConfig`'s `testTimeout` does not reach it, so an unbudgeted `waitFor` around a background dynamic import is a wall-clock budget on module RESOLUTION and flakes under contention: `conclusion-lazy.test.tsx`'s `T-WEB-S289` nonogram arm failed **alone** (1338/1339, 96/97 files) on #163's first CI gate — an archive PR touching nothing in `src/play/**`, `src/nonogram/**` or the conclusion graph — and passed on a re-run that was a real execution (`cache miss, executing …`), not a replay. Read a lone red there as contention, confirm with the re-run's cache-miss line, and give the `waitFor` an explicit CI-anchored budget **in the ticket that OWNS the test** (#145), never in the unrelated PR whose gate happened to surface it: retuning it there makes that PR the place a future bisect lands. Ceiling, not target: over `budget / 2` diagnose and record, **never raise on the tripwire alone** — only a budget decision 2 never derived whose trigger fires is *set* (ADR-0055 (p)); `/ 2` not `/ 4`, since `budget = anchor × 4` makes `/ 4` the anchor. On the 2-vCPU gate a CPU-bound test's duration is set by the CPU share it gets beside whatever siblings run concurrently (sudoku `P1` 35 s → 155 s on an unchanged generator, ADR-0055 (l)), so a `budget / 2` tripwire can be crossed with no trigger touched — read the sudoku lines against 312 500 / 50 000 on any gate log you open; a hit on unchanged code is the gate's shape (#123), not the test. Full record: ADR-0055 (j)–(p) (#109, plan 051).

10. **[2026-08-14] CI runs on `pull_request` ONLY — "CI green on main post-merge" no longer exists as handoff evidence, and PR runs auto-cancel on a new push**
   Do instead: cite the PR's own `gate` run (the ruleset-required context) as the merge evidence; never re-add `push: [main]` to buy back a signal the ruleset already enforces pre-merge. A `gate` showing "cancelled" means a newer commit superseded it, NOT a failure — read the newest run. `.github/workflows/impeccable.yml` is deliberately left un-keyed: its `deployment_status` ref is a raw commit SHA (Vercel sets `deployment.ref` to the 40-char SHA), so concurrency there would buy nothing and could let the miolos-api event cancel the in-flight miolos-web scan. Diagnose a missing `gate` with `gh pr view <n> --json mergeable,mergeStateStatus` BEFORE re-pushing; the fix is `git merge origin/main`, and the gate runs on the first try after it. **A DIFFERENT failure has the same smell and a different cure: a `gate` that EXISTS and sits `QUEUED` forever** (53 min with nothing else running, #67) is a stuck run on GitHub's side — `gh api …/runs/<id>/cancel` answers **HTTP 500** and `gh run rerun` says *"already running"*, so neither escape works. **Close and reopen the PR**: `reopened` is a default `pull_request` trigger type, a fresh run picks up immediately, and no empty commit pollutes the history. Never read a long queue as a red.

## Shell & Command Reliability
1. **[2026-07-31] Frontier query for open unblocked issues**

2. **[2026-07-31] `vercel env pull` appends `.env*` to `.gitignore`; no `psql` on this box**
   Do instead: pull to an absolute path OUTSIDE the repo (`vercel env pull <scratchpad>/x.env --environment=production` from the app dir) — `.gitignore` stays untouched; apply migrations with a temp script over `@neondatabase/serverless` (`neon(url).query(...)` per statement, split on `--> statement-breakpoint`), then delete script + env file (#21 precedent). A script living in the scratchpad can't resolve the package — import the absolute path `<repo>/packages/db/node_modules/@neondatabase/serverless/index.mjs`; and `sql.query()` returns a plain row ARRAY, not `{rows}` (#30 precedent).
3. **[2026-08-13] vitest 4 has no `--concurrency` flag; and a mocked `fetch` that returns ONE shared Response poisons multi-consumer screens**
   Do instead: serialize with `--maxWorkers=1`; in tests where several clients share the fetch stub (streak + stats on the conclusion), return a fresh Response per call or `deferred.then((r) => r.clone())` — a Response body reads once. **turbo, though, has both `--concurrency` and `TURBO_CONCURRENCY`, and the CLI flag BEATS the env var**: `TURBO_CONCURRENCY=10 turbo run … --concurrency=2` runs at **2**, silently, so a measurement that thinks it is overriding a script's flag is measuring the flag. Passing `--concurrency` twice is a hard error ("cannot be used multiple times"), so a flag on a script is **not** overridable while an env var on the script is. `turbo.json`'s top-level `concurrency` is **global** (no per-task form exists in turbo's schema) and any value below 3 breaks `pnpm dev` outright ("You have 2 persistent tasks but turbo is configured for concurrency of 2"). **The repo DOES ship a cap as of #114 (ADR-0057): `"test": "TURBO_CONCURRENCY=2 turbo run test"`, on the root `test` script only** — `dev`, `typecheck` and `build` are untouched, and the CI gate overrides it with `MIOLOS_TEST_DB_TIMING=1 pnpm test --concurrency=10`. **The inline env assignment is the only form that works**: a `--concurrency=2` baked into the script cannot be overridden (flag beats env var, and a second flag is a hard error), and `turbo.json`'s key is global. `${TURBO_CONCURRENCY:-2}` was rejected too — ambient-honouring means the `TURBO_CONCURRENCY=1` agent sessions exported for months would silently keep binding. Overriding is `pnpm test --concurrency=N`: pnpm forwards trailing flags verbatim and echoes the resolved command line, which is also the cheapest proof of what actually ran.
4. **[2026-08-14] `gh api repos/…/branches/main/protection` 404s "Branch not protected" — and main IS protected, by a RULESET the classic API cannot see**
   Do instead: check `gh api repos/fernandolisboa/miolos/rulesets` then `…/rulesets/<id>` before concluding anything about main. `protect-main` (id 20162549, active, no bypass actors) requires PRs, squash-only merges, and the **`gate`** status context — so the gate is enforced pre-merge and nothing may push to main directly.

Dirty tree: stash the dirty file (`.claude/napkin.md` is the usual culprit), checkout main, pull, pop, then delete local+remote branch manually. **Linked worktree** (`git worktree list` shows more than one entry): the checkout-main step cannot run where the branch is checked out elsewhere, so it fires on every merge driven from a per-issue worktree — it hit both of this session's, #122 and #124. Merging from the main checkout avoids it; `git worktree list` before `gh pr merge` is the cheap check.

7. **[2026-08-14] `pnpm add <pkg>@latest` now FAILS for anything published in the last 7 days, and `pnpm install --frozen-lockfile` fails the same way on any too-young lockfile entry (`minimumReleaseAge: 10080`)**

2. **[2026-08-21] "Shipped and live" is not "working": a merged SCHEDULED workflow has ZERO runs until its first tick, so nothing has ever exercised it — and `gh run list --workflow=<file>.yml` prints nothing for a workflow with no runs, which reads identically to a healthy quiet one**

Corollaries: a green gate proves the code, never the wiring; the secret a workflow uses and the secret production uses are two copies and only the second was ever exercised; and `--workflow` matches the *file* name, so cross-check `gh workflow list` before reading an empty run list as "nothing wrong". **Resolved 2026-08-21 by rotation** (see item 3) — run 32477211453 is the workflow's first ever `success`. One inference this entry used to carry was WRONG and is worth not repeating: "the publish cron works, so production's value is good" proves nothing, because that cron's sender and receiver both read the same variable and it succeeds whatever the value is. Production was authoritative for a different reason — it is the *receiver*.
3. **[2026-08-21] Changing a production env var on Vercel: `turbo-ignore` silently skips the redeploy, and a Sensitive var can never be copied — only rotated**
   Two traps that compound. (a) `apps/api/vercel.json` sets `"ignoreCommand": "npx turbo-ignore"`, so a production build with **no diff under `apps/api`** is skipped — the 6-second `Canceled` rows in `vercel ls miolos-api --prod`. `vercel --prod` after `vercel env add` therefore does NOT bake the new value in; whether `--force` defeats the ignore step is undocumented. Do instead: land a real commit touching `apps/api/**` (a docblock counts) and let the merge be the redeploy; confirm with `vercel inspect <url>` showing `● Building` then `● Ready`, not by assuming. **The visible tell is in the PR checks**: a skipped build reports `Canceled by Ignored Build Step` and still shows as `pass`, so green checks are not evidence the value landed — seen on both the CRON_SECRET and POSTHOG_KEY activations (2026-08-21), where the branch's own preview builds were skipped while production correctly built, because turbo-ignore compares against the last deployment *of that target*. (b) A var marked **Sensitive** is write-only: `vercel env pull` writes the literal string `[SENSITIVE]` in place of the value and `vercel env run` delivers it empty, so two holders of one secret can never be reconciled by copying. Do instead: generate a new value, write it to both with `vercel env add … --force --sensitive -y` and `gh secret set` from one shell variable, then force the redeploy. Ordering matters: between the env write and the redeploy, Vercel's cron sender has the new value while the deployed function still checks the old one, so anything Vercel-cron-driven 401s in that window — stay clear of `/cron/publish`'s `0 6 * * *` UTC tick.
