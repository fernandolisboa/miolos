   Do instead: run the file through the repo's `code()` stripper (the `function code(` helper in `eslint-db-wall.test.ts` — cited by symbol, not by line, because the line moves — this very citation was `:812`, was `:888` on `main`, and moved twice more inside one PR's review rounds; also in `archive-routes.test.ts`) before any `toContain`/`not.toContain`/`matchAll` assertion over source. 4. **[2026-08-15] A vitest timeout sized off an ISOLATED local run under-shoots CI by 4-9x — and the ">10s locally" trigger excludes every test that actually flakes**
   Do instead: anchor on the highest **measured** figure — CI where one exists, worst **contended** local otherwise, **never a single-file run** — then ×4, rounded up to the next 5s, arithmetic in a comment beside the test. Trigger: over **40%** of the applicable budget (2s of `testTimeout` 5s, 4s of `hookTimeout` 10s; the hook half is unswept except PGlite's `createTestDb`, instrumented at #114 behind `MIOLOS_TEST_DB_TIMING=1`). **A bare local `pnpm test` is CAPPED at turbo concurrency 2 (#114), so it is never a "contended" anchor** — the uncapped command is `pnpm test --force --concurrency=10`, green on the 16 GB / 8-core box with #120's worker bound and a legal local anchor again, but **CI gate logs stay the preferred source**; no eligible anchor → record that as the reason the budget is not re-derived. Samples from a worker configuration nothing ships (pre-#120 `apps/web` at `cpus − 1`) are history, not anchors (ADR-0055 (o)); a capped run under-shoots CI and `turbo run test`. **Never size from a run in which anything timed out**: a killed test reports the wall, so that run's max is censored and turbo's sibling-kill biases the rest low. The anchor is a sample max, not a bound — a later session exceeding it is the estimator working, so **say so in the comment**: a recorded max owes an update only when a sample crosses the **trigger**, never on every new gate row, and a bare "max = N" goes stale on the next push (#109's own gate moved `T-WEB-S43` 944 → 990 ms mid-review; the next row came back at 666). Where a whole file shares one cost driver, budget the **file** (`vi.setConfig`), not whichever test runs first. Ceiling, not target: over `budget / 2` diagnose and record, **never raise on the tripwire alone** — only a budget decision 2 never derived whose trigger fires is *set* (ADR-0055 (p)); `/ 2` not `/ 4`, since `budget = anchor × 4` makes `/ 4` the anchor. On the 2-vCPU gate a CPU-bound test's duration is set by the CPU share it gets beside whatever siblings run concurrently (sudoku `P1` 35 s → 155 s on an unchanged generator, ADR-0055 (l)), so a `budget / 2` tripwire can be crossed with no trigger touched — read the sudoku lines against 312 500 / 50 000 on any gate log you open; a hit on unchanged code is the gate's shape (#123), not the test. Full record: ADR-0055 (j)–(p) (#109, plan 051).

8. **[2026-08-17] Turbo caches gate runs, so a cached re-run is a log REPLAY, not evidence — and the PGlite `beforeAll` class is MEASURED and AVOIDED BY A CAP, never closed**
   Do instead: re-run gates for PR-body evidence with `--force`. **`TURBO_CONCURRENCY=1` is RETIRED as a standing prefix (#107, ADR-0055):** the `testTimeout` half of the flake is fixed and measured, 1 is the slowest setting measured (67s vs 56-59s uncapped), and **a red root `pnpm test` is a finding again** — diagnose before re-running any `Test timed out in Nms`, any assertion failure, any red in a package you did not touch. **#114 (ADR-0057) retires the carve-out this item used to carry** — the PGlite hook class is no longer unmeasured, and the population is **26 files across `apps/api` (18) and `packages/db` (8)**, not ~20 in one package. Cause: **memory exhaustion**, not the hook and not CPU — six package suites × `cpus-1` workers each outrun an 8-core/15.5GB box and swap thrash turns a 1s WASM boot into a 50s one. Fix: `"test": "TURBO_CONCURRENCY=2 turbo run test"`, inline so a caller's flag still wins. **WHAT REMAINS, and it is the half that gets forgotten: the class is AVOIDED, not CLOSED.** At default fan-out it still fires, and three shipped paths run that configuration — `turbo run test` invoked directly, `pnpm test --concurrency=10`, and **the CI gate, which is deliberately uncapped** (its `maxWorkers` collapses to 1, so a cap would relieve nothing and cost ~+55%). CI's hook cost is measured for the FIRST time by #114's own gate, via `MIOLOS_TEST_DB_TIMING=1`. And a box with a higher cores-to-RAM ratio re-opens #114 outright, because the cap bounds packages and not workers. Still not covered by any of this: turbo's `[ELIFECYCLE]` sibling-termination noise, which is not a test failure at all. A hit is a log REPLAY, so "6 cached, 6 total" is evidence that inputs are unchanged, never that the checks executed here — true locally (`.turbo/cache` survives across sessions) and in CI (restored from an earlier run). The Vercel remote cache that made this cross-MACHINE is gone as of `chore/supply-chain-and-cache`; `.turbo/cache` via `actions/cache` replaced it, so nothing is shared across machines any more.
9. **[2026-08-14] `impeccable detect` is per-viewport AND data-dependent — today's green does not imply tomorrow's, and a copy edit can red it**
   Do instead: check BOTH steps of the detect job (`/estatisticas` failed mobile-only on first-viewport-column-overflow, `0311f32`); and on any page whose CONTENT grows with the calendar or whose LABEL is a template, measure the worst case rather than today's — #31 hit this twice, `first-viewport-column-overflow` at 21 archived rows (due 2026-08-22) and `all-caps-body` at 31 chars once `← <mês>` became `Mês anterior · <mês>` (due 2026-10-01, four months in twelve, forever). Both were invisible to CI and to any commit. Thresholds are literal: `all-caps-body` = >30 chars of DIRECT text under `text-transform: uppercase`, no interactive/`nav` exemption. Reproduce locally with `impeccable detect file://…` over the real component + real stylesheet (CSS-module names unhashed), and pin the shape with a test.
10. **[2026-08-14] CI runs on `pull_request` ONLY — "CI green on main post-merge" no longer exists as handoff evidence, and PR runs auto-cancel on a new push**
   Do instead: cite the PR's own `gate` run (the ruleset-required context) as the merge evidence; never re-add `push: [main]` to buy back a signal the ruleset already enforces pre-merge. A `gate` showing "cancelled" means a newer commit superseded it, NOT a failure — read the newest run. `.github/workflows/impeccable.yml` is deliberately left un-keyed: its `deployment_status` ref is a raw commit SHA (Vercel sets `deployment.ref` to the 40-char SHA), so concurrency there would buy nothing and could let the miolos-api event cancel the in-flight miolos-web scan. Corollary for caching: Actions caches are branch-scoped and nothing writes main's scope any more, so every PR's FIRST `gate` run is cold and warmth only accrues across pushes to the same PR — don't read a cold first run as a cache bug. **And a CONFLICTING PR produces no `pull_request` run at all** (#113, step 7): when a sibling merges to main and the branch goes `mergeStateStatus: DIRTY`, GitHub cannot build the merge ref, so pushing produces `Impeccable` (which fires on `deployment_status`) and **silently no `gate`** — an absent required context, not a failed one. Diagnose a missing `gate` with `gh pr view <n> --json mergeable,mergeStateStatus` BEFORE re-pushing; the fix is `git merge origin/main`, and the gate runs on the first try after it.

## Shell & Command Reliability
1. **[2026-07-31] Frontier query for open unblocked issues**
   Do instead: `gh api "repos/fernandolisboa/miolos/issues?state=open&per_page=100" --jq '.[] | select(.pull_request == null) | select((.issue_dependencies_summary.blocked_by // 0) == 0) | "#\(.number) \(.title)"'`
2. **[2026-07-31] `vercel env pull` appends `.env*` to `.gitignore`; no `psql` on this box**
   Do instead: pull to an absolute path OUTSIDE the repo (`vercel env pull <scratchpad>/x.env --environment=production` from the app dir) — `.gitignore` stays untouched; apply migrations with a temp script over `@neondatabase/serverless` (`neon(url).query(...)` per statement, split on `--> statement-breakpoint`), then delete script + env file (#21 precedent). A script living in the scratchpad can't resolve the package — import the absolute path `<repo>/packages/db/node_modules/@neondatabase/serverless/index.mjs`; and `sql.query()` returns a plain row ARRAY, not `{rows}` (#30 precedent).
3. **[2026-08-13] vitest 4 has no `--concurrency` flag; and a mocked `fetch` that returns ONE shared Response poisons multi-consumer screens**
   Do instead: serialize with `--maxWorkers=1`; in tests where several clients share the fetch stub (streak + stats on the conclusion), return a fresh Response per call or `deferred.then((r) => r.clone())` — a Response body reads once. **turbo, though, has both `--concurrency` and `TURBO_CONCURRENCY`, and the CLI flag BEATS the env var**: `TURBO_CONCURRENCY=10 turbo run … --concurrency=2` runs at **2**, silently, so a measurement that thinks it is overriding a script's flag is measuring the flag. Passing `--concurrency` twice is a hard error ("cannot be used multiple times"), so a flag on a script is **not** overridable while an env var on the script is. `turbo.json`'s top-level `concurrency` is **global** (no per-task form exists in turbo's schema) and any value below 3 breaks `pnpm dev` outright ("You have 2 persistent tasks but turbo is configured for concurrency of 2"). **The repo DOES ship a cap as of #114 (ADR-0057): `"test": "TURBO_CONCURRENCY=2 turbo run test"`, on the root `test` script only** — `dev`, `typecheck` and `build` are untouched, and the CI gate overrides it with `MIOLOS_TEST_DB_TIMING=1 pnpm test --concurrency=10`. **The inline env assignment is the only form that works**: a `--concurrency=2` baked into the script cannot be overridden (flag beats env var, and a second flag is a hard error), and `turbo.json`'s key is global. `${TURBO_CONCURRENCY:-2}` was rejected too — ambient-honouring means the `TURBO_CONCURRENCY=1` agent sessions exported for months would silently keep binding. Overriding is `pnpm test --concurrency=N`: pnpm forwards trailing flags verbatim and echoes the resolved command line, which is also the cheapest proof of what actually ran.
4. **[2026-08-14] `gh api repos/…/branches/main/protection` 404s "Branch not protected" — and main IS protected, by a RULESET the classic API cannot see**
   Do instead: check `gh api repos/fernandolisboa/miolos/rulesets` then `…/rulesets/<id>` before concluding anything about main. `protect-main` (id 20162549, active, no bypass actors) requires PRs, squash-only merges, and the **`gate`** status context — so the gate is enforced pre-merge and nothing may push to main directly.
5. **[2026-08-13] `gh pr merge --squash --delete-branch` from a dirty or LINKED worktree: the GitHub merge SUCCEEDS but the local checkout aborts and the remote branch survives**
   Do instead: after the error, `gh pr view --json state,mergeCommit` before retrying anything — the merge is done and re-running it fails differently. Dirty tree: stash the dirty file (`.claude/napkin.md` is the usual culprit), checkout main, pull, pop, then delete local+remote branch manually. **Linked worktree** (`git worktree list` shows more than one entry): the checkout-main step cannot run where the branch is checked out elsewhere, so it fires on every merge driven from a per-issue worktree — it hit both of this session's, #122 and #124. Merging from the main checkout avoids it; `git worktree list` before `gh pr merge` is the cheap check.
6. **[2026-08-14] `pnpm add <pkg>@latest` now FAILS for anything published in the last 7 days, and `pnpm install --frozen-lockfile` fails the same way on any too-young lockfile entry (`minimumReleaseAge: 10080`)**
   Do instead: check `pnpm view <pkg> time --json` and take a version older than the window. pnpm no longer auto-collects an exclude for you — setting `minimumReleaseAge` explicitly flips `minimumReleaseAgeStrict` on, and the ten machine-written `minimumReleaseAgeExclude` entries deleted in `chore/supply-chain-and-cache` came from that old loose mode. A genuine security patch inside the window gets an exact `name@version` exclude in its own commit, never a bare name or range. `trustPolicy: no-downgrade` fails installs the same way (`ERR_PNPM_TRUST_DOWNGRADE`) when an old-major back-port lacks provenance a newer line already had — `semver@6.3.1` and `eslint-import-resolver-typescript@3.10.1` sit in `trustPolicyExclude` for exactly that reason, verified against `registry.npmjs.org`, not guessed.
